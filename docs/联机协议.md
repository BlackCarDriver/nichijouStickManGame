# 联机协议与接入说明

本文是火柴人大乱斗「聊天室插件房联机」的唯一说明文档：架构、身份、进房与对局流程、
实时同步模型、线上报文、仲裁规则、接入步骤与部署。

相关文档：

- [技术方案](./技术方案.md)：单机部分的系统设计与数值
- 聊天室侧协议：`ChatRoomGameDemo/协议说明.md`（桥接通道、JWT 声明、关闭码）
- 服务端代码：`server/`（Go，复用 `nichijouSDK` 同步副本）
- 客户端代码：`src/net/`

## 1. 架构

```
聊天室外壳（房间页 iframe）
   │  postMessage：READY / INIT / TOKEN / REQUEST_TOKEN / ROOM_STATE / FULLSCREEN_*
   ▼
游戏页面（Vite 产物 dist/，由游戏服务同源托管）
   │  WebSocket /ws?token=<JWT>
   ▼
游戏服务（Go 单二进制）
   ├─ 静态托管 dist/
   ├─ JWT 验签（RS256 / aud / room）
   ├─ 房间：座位、随机地图、逐局结算、拾取/伤害仲裁
   └─ 桥接 WebSocket（X-Plugin-Secret）
        ▼
     聊天室服务端：状态上报 / 公屏事件 / 房间卡片副文案 / 离房 / 关房 / 游戏内聊天
```

为什么必须有服务端：JWT 只允许服务端验签，桥接密钥也只存在于服务端；
游戏页面本身是纯静态资源。

为什么实时同步不走桥接：桥接单帧上限 64 KiB、状态上报最小间隔 1 秒、
事件每分钟 60 条，只适合"房间级"状态，不能承载 20~60Hz 的游戏数据。

### 世界权威（房主 / listen server）

同步模型是**房主权威（listen server）**：服务端只做"房间 + 记录 + 转发"，
世界由**一台客户端（房主）**统一模拟。

```
房主客户端（座位号最小的在线玩家）
  ├─ 模拟所有玩家物理 + 弹道 + 破坏 + 拾取 + 掉落
  ├─ 20Hz 广播 snap（玩家变换 / 动态刚体 / 掉落物坐标）
  └─ 上报 dmg / pick / obj（服务端记录后广播给所有人）
        │  WebSocket
        ▼
游戏服务（Go）：选房主、转发 snap、记录掉落物与已摧毁物体、结算血量/击杀/对局
        │  WebSocket
        ▼
非房主客户端
  ├─ 自己的角色：本地预测（零输入延迟），收到权威快照后平滑纠偏
  ├─ 其它玩家 / 动态刚体（箱子等）：100ms 缓冲插值回放
  └─ 伤害/拾取/破坏：只等权威消息，不自行结算
```

为什么必须这样：Matter.js 的物理**不是跨端确定性的**（帧率、步进合并、
浮点细节、顿帧都会影响结果）。旧版"各端全量模拟 + 互相纠偏"必然漂移：
漂移超过阈值就硬拉 → 出现"跳上二楼又闪回一楼"；动态刚体各算各的 →
出现"我这边 5 个箱子、你那边 4 个箱子"。

现在动态刚体与掉落物位置只有**一个事实来源（房主）**，
所以"A 能跳上的箱子，B 也一定看得见、位置一致"。

## 2. 身份与凭证

| 项 | 来源 | 说明 |
| --- | --- | --- |
| 昵称 | JWT `sub` | 唯一的玩家身份；同名连接会互相顶替 |
| 头像/头像框 | JWT `avatar` / `frame` | 目前仅用于房间列表与结算展示（游戏 HUD 用配色火柴人头像） |
| 是否登录用户 | JWT `registered` | 预留：将来用于存档 |
| 房间 | JWT `room` 必须等于配置的 `roomId` | 防止跨房重放 |

浏览器端（`src/net/ShellBridge.ts`）：

- 启动即向父窗口发送 `READY`，随后接收 `INIT`（展示配置）与 `TOKEN`（JWT + `expireAt`）。
- 令牌只用于建连；连接断开且剩余有效期 < 60 秒时，发送 `REQUEST_TOKEN` 续签后再重连。
- 入站消息校验 `event.source === window.parent`，并锁定首个合法消息的 origin；
  出站使用锁定后的精确 origin（未锁定时才用 `'*'`，仅用于最开始那条 `READY`）。
- 独立打开页面（模板 B / 本地开发）没有外壳续签通道，凭证过期后提示"从房间重新进入"。

服务端（`server/main.go`）：`/ws?token=...` 在升级 WebSocket 前调用
`nichijou.VerifyJWT(token, pub, integrationId, roomId)`，失败返回 401。
头像与昵称一律取验签后的 claims，浏览器上报的昵称不参与鉴权。

## 3. 进房与对局流程

```
连接 → welcome（自己的身份 + 地图列表）
     → match_start（立即进入对局：随机地图、自己的 netId、房主座位、掉落物、血量快照、
                    以及 cache 的一帧 world 全量世界快照）
边打边等人：新玩家随时加入 → 对其他客户端广播 player_join（动态生成火柴人）
一局结束：至少发生过 1 次死亡，且只剩 1 名存活玩家
     → match_end（胜者 + 下一张地图 + 倒计时）
     → 到点自动换图 → 新的一局 match_start（全员满血复活）
```

- **没有大厅、没有准备按钮、没有选图**：连上就进图，可以一边操控一边等人。
- 座位 = 当前在线玩家的入场顺序，最多 `maxPlayers`（默认 8）；超出的旁观。
- 地图由服务端随机挑选，并保证与上一局不同（地图多于 1 张时）。
- 死亡**不会原地复活**：本局内阵亡后保持旁观，等本局结束换图重开。
- **离开 = 死亡**：连接断开（关页面 / 离房 / 刷新）立刻移出对局并计入死亡数，
  只剩一人时本局立即结算；同名重进作为**全新玩家**加入（满血、0 杀、无武器、新座位），
  不保留任何旧状态。
- **房主顺延**：房主（世界权威）离开时，服务端把权威交给座位号最小的在线玩家，
  广播 `host`；新宿主用自己的当前世界状态继续广播快照（会有一帧左右的画面跳变）。
- 结算展示 `roundEndSeconds` 秒（默认 4）后自动开下一局；展示期间新连接会收到
  `waiting`，等下一局开始再进场景。

### 加载进度与开局闸门

进房不是"瞬间开打"，中间有一段加载与确认：

```
连接 → match_start（you=-1，只用于加载地图；此时还没有座位/火柴人）
     → 场景与贴图加载（进度条 0~100%）
     → 一切就绪 → 显示「点击 W 开始游戏」+「观战」
     → 按 W / 点按钮 → 发 enter → 服务端分配座位 → match_start（you=seat）→ 真正开始操控
```

- **只有第一次进入需要按 W**：`enter` 之后本页面会话内每局重开/换图都直接进入，不再弹提示
- 未按 W 前**不占用座位、不会创建火柴人**（别人看不到你，也不会打到"挂机的你"）；
  只有 `enter` 之后才真正加入对局
- 加载进度 = 连接 + 场景贴图（Phaser loader）+ 头像贴图；界面同时显示操作说明
- 移动端（`pointer: coarse`）无法操作：隐藏"点击 W"，突出「观战」按钮；
  点观战后向服务端发送 `spectate`，以旁观身份观看（不占座位、后续开局也不再上场）
- 观战者收到 `you = -1` 的 `match_start`，客户端没有本地角色，镜头跟随场上玩家
- 覆盖层在出现按钮时会显式打开 `pointer-events`（否则按钮看得见点不动）
- **移动端竖屏**：整个游戏层（画布 + DOM 覆盖层）会旋转 90° 铺满屏幕
  （`?rotate=1` / `?rotate=0` 可在桌面强制开关；`node tools/rotate-check.mjs` 可自动回归），
  避免 16:9 画面在竖屏只占中间一条。旋转态下 Phaser 的画布指针坐标不可用
  （浏览器变换后的元素无法被 Phaser 正确换算），当前移动端只能观战，不受影响。

### 死亡回放与结算节奏

- 阵亡后镜头**自动跟到击败自己的那个人**（对手离场/也阵亡时退到第一个存活玩家）；
  屏幕中上方显示「你被 X 用 Y 击败」，Y 来自最后一击的武器 id
  （`fist`/`kick`/`grenade` 等特殊值有中文文案，环境/爆炸有兜底文案）。
- 本局结束不立刻弹结算：服务端下发 `match_end.delayMs`（默认 4s），
  先让玩家看完击败镜头，再弹结算窗；`restartInMs = delayMs + roundEndSeconds`。
- 跳跃高度固定（不随按键时长变化），同一段输入在任何端/任何帧率下轨迹一致，
  也更利于联机预测。

### 界面与聊天

- 聊天输入由**聊天室外壳**负责（`chatMode=game` 时外壳隐藏自己的聊天框，
  游戏内不再重复提供输入框；本地开发模式才有覆盖层输入框用于自测）。
- 聊天室公屏消息经桥接 `chat_in_game` 灌入游戏内，显示为**对应火柴人头顶的聊天气泡**。
- 火柴人头部使用聊天室头像（圆图），头顶固定显示灰色昵称；左上角 HUD 也是圆形头像。
- 画面外的对手会在屏幕边缘显示**该玩家颜色的箭头 + 昵称**，回到视野内即消失。

### 与桥接的映射

| 时刻 | 桥接动作 |
| --- | --- |
| 对局中 | `state_report`：`playing`（阵亡时 `text=阵亡`） |
| 旁观 / 座位满 | `state_report`：`spectating` |
| 每局开始/结束 | `event_log`："对局开始：<地图>" / "对局结束，X 获胜" |
| 玩家入座 | `event_log`："X 加入了游戏" |
| 玩家被击败 | `event_log`："A 击败了 B"（环境/自伤为 "X 阵亡"） |
| 房间卡片副文案 | `room_lp`："对局中-火柴人 n/8" / "结算中-下一局准备" |
| 聊天室公屏消息 | `chat_in_game` → 广播给游戏内所有客户端（聊天记录里标 `(房间)`） |
| 用户离房 | `room_leave` → 关闭该用户连接、移出对局、广播 `player_left` |
| 关房 | `room_closed` → 广播 `room_closed`，停止接纳新连接 |

状态变化后调用 `ScheduleFullReport()`（SDK 会合并 1 秒内的变化并补发全量快照）；
房间卡片文案在每次连接/重连后由 SDK 主动重发。

## 4. 同步模型（v2：房主权威快照 + 本地预测 + 远端插值）

### 4.1 玩家操作

- 每个客户端把自己的 `InputCommand` 以 **60Hz** 上报（`in`），服务端合并后以 **30Hz**
  广播给所有人（含边沿位）。WebSocket 可靠有序，不需要 ACK。
- 房主用这些输入模拟**所有玩家**（自己的和别人的），得到唯一的世界状态。
- 非房主客户端也用这些输入驱动远端玩家的**动作表现**（射击/挥砍/瞄准姿态），
  但位置/速度以房主快照为准。
- 边沿位：`1 跳跃 / 2 攻击 / 4 踢 / 8 替换 / 16 手榴弹`；服务端只下发一次并清零。

### 4.2 权威划分

| 数据 | 权威 | 同步方式 |
| --- | --- | --- |
| 所有玩家位置/速度/着地 | **房主** | `snap`（20Hz）+ 客户端 100ms 缓冲插值 |
| 自己的角色 | 本地预测 + 房主纠偏 | 本地立刻响应；误差 >10px 平滑收敛（≤9px/帧），>240px 才硬对齐 |
| 动态刚体（纸箱/铁球/跷跷板）位置与朝向 | **房主** | `snap.o`（变化才发，1s 一次全量关键帧） |
| 掉落物坐标 / 落点 | **房主** | `snap.d`；服务端记录最新值，中途加入者也拿到落地后的坐标 |
| 生命值 / 护盾 / 死亡 / 击杀 | **服务端** | 房主上报 `dmg` → 服务端结算 → 广播 `hp` |
| 地图物体耐久 / 摧毁 | **房主** | 房主本地结算并发 `obj`；其它端只播受击表现 + `forceDestroyById` |
| 拾取 / 换枪归属 | **房主判定** → 服务端授予 | 房主发 `pick.by`；服务端广播 `pick`（含换下来的旧武器掉落） |
| 投掷武器落地 | **房主** | `drop` → 服务端生成掉落物 → `drop_add` |
| 超级战士护盾 | 玩家客户端上报增量 | `shield` → 服务端钳制后广播 `hp` |
| 一局结束 / 下一张地图 | **服务端** | 最后一人胜出 → `match_end` → 到点自动 `match_start` |

要点：

- **非房主不结算伤害、不扣耐久、不判定拾取**（`DamainSystem`/`DestructionSystem`/`PickupSystem`
  都有 mode 开关），否则 N 端重复结算会打架。
- **房主不信任客户端上报的距离**：拾取由房主用自己的世界判定；
  服务端只保留"普通客户端给自己拾取"的粗略距离校验。
- **联机禁用物理顿帧**：`HitStop` 只保留镜头/音效，绝不 `matter.world.pause()`。
  各端冻结时刻不同会让同一个玩家的轨迹直接分叉。

### 4.3 位置纠偏（为什么不再瞬移）

旧的纠偏是"每 100ms 拿一个权威坐标 + 误差 >140px 直接 setPosition"。
跳跃时 100ms 的位移就有 100px 以上（跳跃初速 17px/step ≈ 1020px/s），
再叠加网络延迟，几乎每次跳跃都会触发硬瞬移，而且是"拉回过去的位置"。

v2 的做法：

1. **远端玩家不做本地预测**：按 `接收时间 - 100ms` 在快照缓冲里做线性插值
   （快照中断时用速度外推，上限 220ms）。因此远端玩家的画面永远是平滑的，
   不会出现一帧几百像素的跳变。
2. **自己的角色做本地预测**（零输入延迟），只在必要的时候纠偏：
   - 目标位置 = 最近一条权威样本按"样本年龄 + 单程延迟"外推；
   - 误差 ≤10px：不处理（避免和预测对着干，产生橡皮筋感）；
   - 误差 10~240px：每帧最多修正 9px（平滑收敛）；
   - 误差 >240px：判定为真脱同步（掉包/长时间卡顿），直接对齐，
     并在 `stats.hardSnaps` 里计数（正常对局应为 0）。
3. 单程延迟来自周期性 `ping/pong` 的平滑估计；渲染延迟 100ms 是刻意的取舍
   （换永不瞬移的更顺滑观感）。

### 4.4 世界状态一致性

- 动态刚体的变换以房主为准；非房主端每帧把刚体"钉"到插值目标上（速度清零），
  视觉会自然跟随，本地碰撞（跳箱子、子弹打箱子）也都基于这个位置。
- 被摧毁的物体由房主广播 `obj`，所有端 `forceDestroyById` 移除；
  id 的唯一性由 `npm run validate`（展开预制件后逐 id 校验）和运行时告警兜底。
- 中途加入：`match_start.world` 带一帧全量快照（玩家位置、动态物体、掉落物），
  客户端在场景创建完成后立即套用，所以"新人看到的是原始地图布局"这个问题不存在。
- 掉落物落点由房主模拟并发在 `snap.d` 里，服务端把最新坐标写进 `match_start.drops`，
  所以中途加入者看到的落点和老玩家完全一致（不再从出生点自己重新掉一次）。
- 房主每 500ms 清理一次掉出地图的刚体与掉落物：
  动态刚体走 `obj`（所有人一致移除），掉落物走 `drop_remove`（服务端同步删记录）。
  否则一个掉出世界的箱子会永远自由落体，既浪费物理，又让两端各自"看到"它。

### 4.5 地图数据的硬性要求

动态刚体（`fixed: false` 的材质、`bodyMode: "loose"` 的预制件）**不能与地面/平台/其它动态体互相重叠**：

- 生成时互相嵌入 → Matter 的分离求解会给它们巨大的弹出速度 → 穿地、飞出地图；
- 旧版 `rustworks` 的纸箱堆就是这种情况（三个 `boxs` 实例重叠 120px，且下半部分埋进地面 80px），
  表现就是"我这边 5 个箱子、你那边 4 个散乱箱子"。
- `npm run validate` 现在会校验**展开后的物体 id 唯一性**；
  位置重叠请用编辑器检查（预览里能直接看到穿模）。

## 5. 线上报文

### 5.1 客户端 → 服务端

| `t` | 字段 | 说明 |
| --- | --- | --- |
| `chat` | `text` | 游戏内聊天（≤160 字，4 条 / 2 秒限频；开发模式用） |
| `enter` | — | 「点击 W 开始」后真正入座；未发送前只旁观/加载，不占座位 |
| `spectate` | — | 主动转为观战：让出座位（**不计死亡**），后续开局不再分配座位 |
| `in` | `seq,mx,jh,cr,ah,kh,sw,aim,e` | 每帧输入；`mx∈{-1,0,1}`，`e` 是边沿位掩码 |
| `pos` | `x,y,vx,vy` | 10Hz 自身位置（**不再广播**，仅服务端做拾取距离粗校验） |
| `snap` | `seq,key,p[],o?,d?` | **房主**广播权威世界快照（20Hz；`key=1` 为全量关键帧） |
| `pick` | `id,by?,swap?` | 拾取请求；房主代他人请求时填 `by`，`swap` 为换下来的旧武器 |
| `dmg` | `target,src,weapon,amount,kind,crit,point,kb,attack,ignoreInvuln` | 伤害上报（仅房主；`src` = 攻击者座位，-1 = 环境；`weapon` 用于死亡回放） |
| `shield` | `amount` | 本地新增护盾（超级战士，仅本人上报） |
| `drop` | `weaponId,ammo,x,y` | 投掷后插不进去的武器落地（仅房主） |
| `obj` | `id` | 地图物体被摧毁（仅房主） |
| `drop_remove` | `id` | 掉落物移除（掉出地图等，仅房主） |
| `ping` | `ts` | 延迟测量 |

非房主发送 `snap/dmg/pick(by)/obj/drop` 会被服务端丢弃（防伪造、防重复结算）。

## 6. 客户端职责划分

| 文件 | 职责 |
| --- | --- |
| `src/net/ShellBridge.ts` | 外壳 postMessage、token 续签、ROOM_STATE、全屏 |
| `src/net/NetClient.ts` | WebSocket 连接/重连/关闭码处理/消息分发 |
| `src/net/RoomController.ts` | 连接与场景生命周期、覆盖层、延迟测量 |
| `src/net/OnlineMatch.ts` | 对局同步：房主快照生成 / 远端插值 / 本地预测纠偏 / 血量·掉落·销毁事件 |
| `src/world/PickupSystem.ts` | 三种模式：单机（本地生效）/ authority（房主替所有人判定）/ client（只做本地预判） |
| `src/world/DestructionSystem.ts` | `setAuthority()`：只有房主扣耐久与摧毁，其它端只播受击表现 |
| `src/ui/Overlay.ts` | 等待提示 / 结算 / 全屏按钮的 DOM 界面 |
| `src/scenes/GameScene.ts` | 单机与联机共用同一套对局逻辑（`init({online})` 区分） |

联机时以下本地系统不创建（改由服务端驱动）：`DropSystem`、`ItemDropSystem`、
`WeaponSpawnerSystem`；`PickupSystem` 进入仲裁模式；`DamageSystem` 挂上网络 sink；
`Player.applyDamage` 被 `netControlled` 短路，改为 `applyNetDamage`。

## 8. 部署

- 生产必须 HTTPS + WSS：游戏页面与 `/ws` 同源，由游戏服务直接托管 `dist/`。
- 反向代理需要支持 WebSocket 升级（`Upgrade` / `Connection` 头）。
- **一个插件房 = 一份 `integration.json` = 一个游戏服务实例**：桥接通道每房只允许
  一条连接，密钥版本高者优先。多房间就多实例（不同端口/目录/配置）。
- 服务端需要能主动访问聊天室的桥接地址与 WSS。
- 密钥只保存在服务端；`plugin_jwt.pub.pem` 可以公开但建议按环境分发。
- 常用参数（`config/plugin_config.json`）：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `addr` | `:8092` | 监听地址 |
| `staticDir` | `../dist` | 前端产物目录 |
| `dataDir` | `../data` | 地图/武器/物品数据（服务端读掉落与出生点） |
| `maxPlayers` | `8` | 座位数（超出者旁观） |
| `roundEndSeconds` | `4` | 每局结算展示时长（到点自动换图重开） |
| `allowDevIdentity` | `false` | 仅本地联调允许假身份（务必保持关闭） |

环境变量可覆盖接入凭证：`CHATROOM`、`ROOM_ID`、`INTEGRATION_ID`、`BRIDGE_SECRET`、
`EXCHANGE_SECRET`、`SECRET_VERSION`。

## 9. 已知限制 / 后续

- 本局内阵亡后不能复活，只能等本局结束（换图重开）。
- 没有观战自由镜头：旁观者跟随场上第一个玩家。
- 模板 B（新标签页）没有续签通道，凭证过期需从房间重新打开。
- 聊天室头像加载依赖对方域名的 CORS（当前 `nichijou.cn` 允许）；失败时退回程序化火柴人头像。
- **远端玩家有约 100ms 的渲染延迟**（插值缓冲），这是"永不瞬移"的刻意取舍。
- **房主顺延会有一帧画面跳变**：新宿主从自己当前的（插值过的）世界状态接管。
- 房主上行带宽 ≈ 快照 20Hz（8 人 + 数十个动态物体，约 10~30KB/s），
  房主机器较差时全场手感一起变差（listen server 的固有权衡）。
- 命中判定用房主当前状态，未做 lag compensation：高延迟玩家打移动目标会略"迟"。
- 反作弊是宽松校验（房主可信 + 自伤/超量/频率上限），定位是聊天室内的休闲对战。
